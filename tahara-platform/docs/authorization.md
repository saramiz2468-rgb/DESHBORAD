# מודל הרשאות – אכיפה בכל השכבות

> סטטוס: מתוכנן לשלב 2 (משתמשות) ושלב 7 (מנהלות). בשלב 1 אין session ואין נתונים.

## עיקרון

בדיקת זכאות ב-Proxy/Middleware **אינה** אמצעי אבטחה. כל פעולת קריאה וכתיבה נאכפת **בשרת וגם ב-RLS**, כך שעקיפה של שכבה אחת אינה מספיקה.

| שכבה                                     | מה נבדק                                                                                             | הערות                                                                                |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 1. Proxy (`apps/*/src/proxy.ts`)         | קיום session, הפניה ל-`/login`                                                                      | UX בלבד. בשלב 1: CSP + no-store + נעילת admin                                        |
| 2. שרת – Server Actions / Route Handlers | `requireUser()`; לכתיבה גם `requireEntitlement()` – קריאה טרייה מה-DB, לא מתוך ה-JWT; אימות קלט zod | נקודת אכיפה יחידה: `apps/web/src/server/authz.ts`. בדיקת lint/טסט שכל action קורא לה |
| 3. RLS ב-Postgres                        | קריאה: `user_id = auth.uid()`. כתיבה: גם `app.has_active_entitlement(auth.uid())`                   | חל על כל טבלה ב-`med`, `hal`, `support`, `app`                                       |
| 4. אילוצי DB                             | `user_id default auth.uid()`; trigger שמונע שינוי `user_id`; `check` על טווחים                      | מונע "העברת" שורה בין משתמשות                                                        |

### קריאה לאחר ביטול זכאות

קריאה, ייצוא ומחיקה של הנתונים העצמיים נשארים זמינים גם ללא זכאות פעילה (זכות עיון). כתיבה חסומה.

## מנהלות

- טבלת `admin.admins` (user_id, role). כניסה: Magic Link + TOTP; כל פעולה דורשת `aal2` ב-JWT.
- **לאפליקציית הניהול אין `SUPABASE_SERVICE_ROLE_KEY`**. כל פעולה = RPC ב-schema `admin` (`security definer`) שבודק `admin.is_admin()` + `aal2`, מבצע ורושם ב-`admin.audit_log`.
- ל-schemas `med` ו-`hal` **אין grants ואין policies** לתפקיד המנהלת או לפונקציות ה-RPC של הניהול.
- תצוגת משתמשות = view מצומצם על `auth.users` (מייל, תאריך הצטרפות, כניסה אחרונה) + סטטוס זכאות. ללא ספירת רשומות רפואיות/הלכתיות.

## service role

משמש **רק** ב-webhook של ספק התשלום (`apps/web/src/app/api/webhooks/payments`, שלב 6) לרישום רכישה וזכאות, לאחר אימות חתימה ו-idempotency. לעולם לא בקוד לקוח, לעולם לא ב-`NEXT_PUBLIC_*`, לעולם לא באפליקציית הניהול.

## בדיקות מתוכננות

- pgTAP: משתמשת A ↛ נתוני B (select/insert/update/delete); ללא זכאות → כתיבה נכשלת; מנהלת → 0 שורות ושגיאת הרשאה ב-`med`/`hal`; RPC ניהול ללא `aal2` נכשל.
- אינטגרציה: כל Server Action ללא session/זכאות מחזיר שגיאה ולא כותב.
- E2E: ניווט ישיר לנתיב מוגן ללא session.
